# Athlytic – planning document

Athlytic is a mobile-first PWA that turns wearable data into analytics and insights. This document records the
planning findings; implementation details live in [ARCHITECTURE.md](ARCHITECTURE.md), [ANALYTICS.md](ANALYTICS.md)
and [GARMIN.md](GARMIN.md).

## 1. PWA limitations that shape the design

| Area | Limitation | Consequence in Athlytic |
| --- | --- | --- |
| iOS storage | Safari may evict site data after ~7 days without use unless the app is installed to the home screen. Quota is limited. | Install is encouraged in Settings. Offline data is a *cache* (IndexedDB, 7 days); the source of truth is Postgres. |
| iOS install | No `beforeinstallprompt`. Install is manual via *Share → Zum Home-Bildschirm*. | Settings shows iOS-specific instructions; Android uses the native prompt. |
| Background Sync / Periodic Sync | Not available on iOS Safari; Chromium only. | Sync runs on app start, on reconnect and when the app returns to the foreground. Actual freshness comes from server-side sync. |
| Push notifications | iOS only for installed PWAs (16.4+), and permissions are fragile. | Not part of the MVP. |
| Splash screens | iOS needs one `apple-touch-startup-image` per device size. | Generated by `scripts/generate-icons.mjs` for current iPhones. |
| Service worker updates | A new worker waits until all tabs close. | `registerType: 'prompt'`: the user confirms the update, so state is never lost mid-edit. |
| Bluetooth / direct device access | Web Bluetooth is not available on iOS and cannot read Garmin's protocol. | All device data comes via the cloud. |
| Health stores | See section 4. | Import mechanisms instead of direct integration. |
| Maps offline | OSM tile usage policy forbids bulk prefetching. | Tiles are cached only as they are viewed (cache-first, 400 entries, 30 days). |

## 2. Garmin feasibility

See [GARMIN.md](GARMIN.md) for details. In short:

- There is **no public, self-service Garmin API**. Access goes through the Garmin Connect Developer Program (Health /
  Activity APIs), which requires an application and approval, and is intended for business use. The user plans to
  obtain access; endpoint paths and payload shapes in this repository are **modelled on the documented Health API but
  not yet verified against a real account**.
- Unofficial scraping libraries (e.g. reverse-engineered Garmin Connect logins) violate the terms of service, break
  often and would require storing the user's Garmin password. They are explicitly **not** used.
- The architecture therefore isolates Garmin behind a `DataProvider` interface and ships a deterministic fixture
  client, so the whole product works and can be demonstrated before access is granted.

## 3. Features that need native capabilities

| Feature | In a PWA | Alternative |
| --- | --- | --- |
| Reading Apple Health / HealthKit | Impossible (no web API) | Garmin cloud as primary source; Apple Health XML export import (post-MVP) |
| Reading Android Health Connect | Impossible from the web | CSV/FIT import; a Capacitor/TWA wrapper could bridge it later |
| Continuous background sync | Not on iOS | Server-side sync; foreground sync |
| Live workout recording / GPS tracking | Geolocation only works in the foreground and the screen must stay on | Out of scope – Athlytic analyses, it does not record |
| Reliable push for new insights | iOS limited | In-app insight feed |
| Widgets / complications | Not possible | None |
| Direct FIT file from watch | No USB/BLE access on iOS | Manual FIT upload (post-MVP) |

## 4. Apple Health and Health Connect

- **Apple Health**: HealthKit is native-only. The user can export all data (`export.zip` containing `export.xml`)
  from the Health app. A future importer can parse this in a Web Worker and map it to the normalized model with
  `source = 'apple_health'`. Exports are large (hundreds of MB), so parsing must be streaming.
- **Health Connect**: Android-only native SDK; no web API. Options are CSV/FIT file import or a native wrapper app.
- Neither is promised for the MVP. The database stores a `source` per row and provider priorities are defined in
  `PROVIDER_PRIORITY` (`_shared/provider.ts`), so these sources can be added without schema changes.

## 5. Database schema

Defined in [`supabase/migrations/20261104090000_init_schema.sql`](../supabase/migrations/20261104090000_init_schema.sql).

| Table | Purpose |
| --- | --- |
| `profiles` | One row per user (created by trigger): display name, birth year, max HR, resting HR override, step goal, locale, timezone. |
| `provider_connections` | A user's link to a provider (status, sync state, cursor, `history_start`, `last_synced_at`, `last_error`). |
| `provider_credentials` | AES-256-GCM encrypted token. RLS on, **no client privileges**. |
| `sync_runs` | Audit log of every sync (kind, range, counts, errors, duration). |
| `raw_payloads` | Original provider JSON, versioned by hash. Not readable by clients. Enables re-normalization. |
| `daily_metrics` | One row per user/day/source: steps, HR, HRV, stress, Body Battery, load, … with `fetched_at` provenance. |
| `sleep_sessions` | Sleep sessions with stages and scores. |
| `intraday_samples` | Time series (HR, stress, Body Battery) per day. |
| `activities` | Normalized activities with `external_id`, `duplicate_of`, zones, training effect, summary polyline. |
| `activity_details` | Heavy data fetched on demand: splits/laps, GPS track, cadence/elevation series. |
| `activity_user_data` | User notes kept separate so a re-sync never overwrites them. |

Key rules:

- Every table has `user_id` and row-level security: users read only their own rows and may write only `profiles` and
  `activity_user_data`. Everything else is written by edge functions with the service role.
- Idempotency: unique keys on `(user_id, source, date)` and `(user_id, source, external_id)`; raw payloads are unique
  on `(connection_id, resource_type, external_id, payload_hash)`.
- Duplicate activities from several sources are linked with `duplicate_of` and excluded from analytics.
- Incomplete data is `NULL`, never `0`.

## 6. Application architecture

See [ARCHITECTURE.md](ARCHITECTURE.md). Layers: UI (features/components) → hooks (TanStack Query) → repository
interface → Supabase or demo implementation. Analytics is a pure module with no React or network imports.
Provider code and normalizers are shared between Vite and Deno functions.

## 7. MVP scope

Included (implemented):

- Email + password auth (Supabase), multi-user with RLS; demo mode without backend (used for GitHub Pages).
- Dashboard, Analytics (day/week/month/year, comparisons, records, metric detail), Activities (list, detail, zones,
  splits, elevation, cadence, Leaflet/OSM route), Recovery & Health, Insights, Methods.
- Garmin provider via fixtures plus a real HTTP client behind a feature flag; historical import (730 days) and
  incremental sync with a 3-day overlap.
- PWA: installable, offline cache of last-synced data, status indicator, prompt-based updates, safe areas.
- German UI, i18n-ready; metric units; light/dark themes.

Deferred: Apple Health XML import, FIT/CSV import, push notifications, additional languages, tests (explicitly
skipped for now; the analytics module is pure and ready to be tested), offline write queue.

## 8. Decisions taken (from the planning questionnaire)

- Scope: planning plus milestones 1–6. npm. Supabase local first; email + password only; multi-user.
- Garmin Health API key will be obtained by the user; until then fixtures. Forerunner 970, hiking and cycling first.
- German only, metric units. OpenStreetMap + Leaflet. GitHub Pages hosting (demo mode).
- Tests skipped for now.

## 9. Open decisions

1. **Garmin access tier and real payloads**: confirm endpoints/fields once a key is available (see GARMIN.md).
2. **Hosting of the real backend**: a hosted Supabase project costs money; the live site stays in demo mode until
   the user creates one.
3. **Token model**: GARMIN personal tokens vs. OAuth per user – depends on the program the key belongs to.
4. **Data retention / GDPR**: account deletion cascades through `user_id` foreign keys; a user-facing export is not
   built yet.
5. **Offline writes**: user edits currently require connectivity; a mutation queue is possible if needed.
6. **Tests**: to be added before a public release.
